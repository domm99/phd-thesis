\chapter{Software Tools and Experimental Infrastructure}
\label{chap:frameworks}
\minitoc
%----------------------------------------------------------------------------------------

The contributions of this thesis require both an implementation environment
 for collective coordination and experimental tools that reproduce the
 conditions under which cooperative learning takes place.
%
This chapter presents two frameworks developed to meet these needs:
 Phyelds, a native Python implementation of \gls{AC}, and ProFed,
 a benchmark for constructing proximity-based non-IID federated learning scenarios.
%
Phyelds connects aggregate programs with Python-based learning and simulation
 workflows, whereas ProFed makes the relationship between spatial organization
 and data heterogeneity an explicit part of experimental design.
%
The two frameworks serve complementary purposes and can be used independently:
 one provides coordination abstractions, while the other supplies controlled
 data partitions for evaluating learning algorithms.

%=============================================================================
\section{Phyelds: Aggregate Computing in Python}
\label{sec:phyelds}
%=============================================================================

\subsection{Motivation and Design Goals}

The work presented in this thesis required aggregate programs to interact
 directly with machine-learning models, training procedures, and multi-agent
 environments.
%
However, established \gls{AC} implementations, including Protelis, ScaFi, Collektive
 and FCPP, target Java, Scala, Kotlin and C++, respectively, whereas contemporary
 machine-learning workflows are predominantly developed in Python.
%
Combining these environments requires a cross-language interface (e.g., ScalaPy~\cite{DBLP:conf/scala/LaddadS20}) 
 for model parameters, tensors, datasets, and simulation state, introducing additional
 complexity into development and experimentation.

Phyelds addresses this barrier through a native Python implementation of
 \gls{AC}~\cite{DBLP:conf/coordination/AguzziDFV26}.
%
It implements the execution model and coordination constructs introduced
 in~\Cref{sec:field-calculus} through an API that follows Python's imperative
 and object-oriented conventions.
%
Aggregate coordination can therefore be embedded in ordinary Python
 applications and combined with libraries such as PyTorch and TensorFlow
 without moving data or control across language boundaries.
%
This also makes the framework suitable for interactive development in
 notebooks and for integration with Python-based robotics and simulation software.

Three goals guided the design.
%
First, aggregate programs should resemble conventional Python code, allowing
 developers to use familiar function calls, conditionals, and state updates.
%
Second, the architecture should remain lightweight and modular, so that
 applications can incorporate the components they need and supply their own
 execution environment.
%
Third, values manipulated by aggregate programs should retain their existing
 Python interfaces whenever possible.
%
Coordination functions can consequently operate on numbers, collections,
 model parameters, and tensors without requiring a separate application-level
 representation for each kind of data.

\subsection{Execution Architecture}
\label{sec:phyelds-architecture}

The implementation comprises five modules:
 \emph{VM}, \emph{Data}, \emph{Calculus}, \emph{Library}, and \emph{Simulator}.
%
Their dependencies are summarized in~\Cref{fig:phyelds-architecture}.
%
The VM and Data modules provide execution and field representations;
 the Calculus module exposes the programming interface;
 the Library module supplies reusable coordination functions;
 and the Simulator module supports experimentation and external integrations.

\begin{figure}[t]
  \centering
  \includegraphics[width=\textwidth]{figures/ch03/phyelds.drawio.pdf}
  \caption{Modular architecture of Phyelds. The VM manages aggregate rounds
   and execution contexts; Data represents persistent state and neighborhood
   values; Calculus exposes Pythonic constructs; Library provides reusable
   coordination functions; and Simulator supplies execution environments.}
  \label{fig:phyelds-architecture}
\end{figure}

\paragraph{Virtual machine.}
The VM module implements the local execution of an aggregate round.
%
Its main abstractions are \texttt{Engine}, \texttt{NodeContext}, and
 \texttt{EngineState}.
%
The context supplies information about the executing device, including its
 identifier, time, and sensor readings, while the engine state retains the
 information required across successive rounds.
%
The engine manages incoming neighbor messages, persistent state, and the
 execution paths used for alignment.

The lifecycle consists of three stages, illustrated
 in~\Cref{lst:phyelds-engine}.
%
Before execution, \texttt{setup} installs the current context, the messages
 received from neighbors, and the previous local state.
%
The aggregate program then executes as an ordinary Python function.
%
Finally, \texttt{cooldown} returns the new state and outgoing messages and
 resets the engine's round-specific execution context.
%
The surrounding runtime stores the state and delivers the messages before
 subsequent executions.

\begin{lstlisting}[language=Python,breaklines=true,
  caption={Lifecycle of an aggregate round in Phyelds.},
  label={lst:phyelds-engine}]
from phyelds import engine

engine.get().setup(
    node_context=node_context,
    messages=received_messages,
    state=previous_state,
)
result = my_aggregate_program()
new_state, messages_to_send = engine.get().cooldown()
\end{lstlisting}

This interface separates coordination semantics from scheduling and
 communication.
%
A simulator or device runtime is responsible for deciding when a round
 occurs and how messages are transported; the engine determines how the
 program interprets those messages and evolves its local state.
%
The API does not require devices to execute in global lockstep: a round
 consumes the neighbor information made available by the runtime.
%
The currently active engine is accessed through a Python
 \texttt{ContextVar}, allowing execution contexts to be kept separate
 when multiple aggregate executions are managed within the same application.

\paragraph{Data representations.}
The Data module represents persistent values through \texttt{State}
 and neighbor values through \texttt{NeighborhoodField}.
%
A \texttt{State} object is a proxy for a value retained between rounds.
%
Alongside the underlying object, it records the execution path associated
 with the stateful operation that created it.
%
This lets the engine associate each stored value with the appropriate
 occurrence of a construct while exposing a Python-like interface to the program.

A \texttt{NeighborhoodField} represents the aligned values available from
 neighboring devices.
%
Internally, it maps device identifiers to values, but the API supports
 operations directly on the field, including arithmetic, combination, and
 aggregation.
%
For example, adding compatible neighborhood fields applies the operation
 to corresponding device values, while \texttt{foldhood} reduces a field
 through a user-supplied binary operator.
%
Convenience methods, including \texttt{min} and \texttt{max}, express common
 reductions without exposing the underlying dictionary.

\subsection{Pythonic Calculus Constructs and Alignment}
\label{sec:phyelds-calculus}

The Calculus module translates the core \gls{FC} constructs into a Pythonic API.
%
Its entry point is the \texttt{@aggregate} decorator, which marks a function
 as part of an aggregate program.
%
Each decorated invocation enters a named execution scope and leaves it when
 the call completes.
%
These scopes contribute to an alignment path, allowing the engine to
 distinguish state and exchanged values belonging to different parts of the program.
%
Alignment is therefore maintained through ordinary function composition,
 without requiring application code to assign identifiers to messages or state.

\paragraph{Persistent state.}
State evolution is exposed through \texttt{remember}.
%
Unlike the functional \texttt{rep} construct, which receives an initial
 value and an update function, \texttt{remember(initial)} returns a setter
 and the current state value.
%
The programmer can inspect that value and decide imperatively whether and
 how to replace it.
%
For instance, a counter is expressed as follows:

\begin{lstlisting}[language=Python,breaklines=true,
  caption={Imperative update of persistent state.},
  label={lst:phyelds-remember}]
set_value, value = remember(0)
set_value(value + 1)
\end{lstlisting}

The initial value is used when the corresponding state is first established;
 later rounds retrieve the value retained at the same aligned execution path.
%
The setter separates access from update, making state transitions explicit
 while allowing the surrounding computation to use ordinary Python statements.

\paragraph{Neighbor interaction.}
The \texttt{neighbors(value)} construct shares a local value and returns a
 \texttt{NeighborhoodField} containing the aligned values received from neighbors.
%
When its argument is a \texttt{State} object, transmission is lazy:
 the stored value is exported when it changes, avoiding repeated exchange
 of unchanged state.
%
This mechanism is useful when the coordinated value is expensive to transmit,
 as can be the case for model parameters.
%
It is an optimization of state exchange; the surrounding runtime still
 determines message delivery and the neighborhood available at each round.

\Cref{lst:phyelds-api} combines persistent state, local sensing, and neighbor
 interaction.
%
The counter increases only while the device's \texttt{active} sensor is true,
 but its value is shared on every execution of the communication construct.
%
Because that construct appears after the conditional, it belongs to the
 common execution scope rather than to either branch.

\begin{lstlisting}[language=Python,breaklines=true,
  caption={State, sensing, and neighbor interaction in Phyelds.},
  label={lst:phyelds-api}]
@aggregate
def active_counter():
    set_counter, counter = remember(0)

    if sense("active"):
        set_counter(counter + 1)

    neighbor_counters = neighbors(counter)
    return neighbor_counters.max()
\end{lstlisting}

\paragraph{Conditional alignment.}
Ordinary Python conditionals require additional handling because branching
 in \gls{FC} also restricts the alignment domain.
%
Devices taking different branches must not exchange values through
 constructs located inside those branches, even if those constructs have
 similar local code.
%
Once execution returns to the common enclosing scope, subsequent constructs
 can again involve devices from both branches.

Phyelds implements this behavior by transforming the source of decorated
 functions through Python's abstract syntax tree.
%
The transformation intercepts \texttt{if} statements and wraps their bodies
 in distinct alignment context managers.
%
\Cref{lst:phyelds-alignment} shows the transformation schematically.
%
The developer writes the original conditional, while the transformed
 version makes the branch distinction visible to the engine.

\begin{lstlisting}[language=Python,breaklines=true,
  caption={Schematic transformation of a Python conditional for alignment.},
  label={lst:phyelds-alignment}]
# Original program fragment
if condition:
    do_something()
else:
    do_other()

# Fragment executed after transformation
if condition:
    with align_left():
        do_something()
else:
    with align_right():
        do_other()
\end{lstlisting}

Together, decorated function scopes and branch contexts preserve the
 distinction between independent subcomputations.
%
This is particularly relevant when reusable functions contain their own
 stateful or communication constructs: each invocation must refer to the
 corresponding distributed computation rather than accidentally reuse
 another invocation's state or neighbor values.

\subsection{Coordination Library and Native Simulation}
\label{sec:phyelds-library}

The Library module builds higher-level coordination functions on top of the
 calculus interface.
%
Its organization follows common aggregate programming concerns:
 device access, time, distance metrics, spreading, collection, gossip,
 and leader election.
%
These functions retain ordinary Python values at their interfaces,
 allowing the same coordination structure to carry sensor readings,
 collections, or model parameters.

\paragraph{Context and distance.}
The device submodule provides \texttt{local\_\allowbreak id}, \texttt{local\_\allowbreak position},
 and \texttt{sense} for accessing the current execution context.
%
Temporal functions provide simulation time, round counters, and decay
 mechanisms for time-dependent behavior.
%
Distance functions supply neighborhood metrics based on spatial positions
 or hop counts, supporting both geometric and topology-based computations.
%
Using a distance field as an argument also allows higher-level functions
 to operate with application-specific notions of proximity.

\paragraph{Spreading and collection.}
The \texttt{distance\_\allowbreak to} function constructs a potential field from
 designated sources.
%
This field provides a direction for information propagation and supports
 functions such as \texttt{broadcast}, which disseminates values from sources,
 and \texttt{cast\_\allowbreak from}, which accumulates information along propagation paths.
%
Collection functions operate in the opposite direction, using decreasing
 potential values to establish routes toward a source.
%
The \texttt{find\_\allowbreak parent} function identifies parent relationships, while
 \texttt{collect\_\allowbreak with} combines contributions using a supplied accumulation
 function.
%
Specialized forms include \texttt{count\_\allowbreak nodes} and \texttt{sum\_\allowbreak values}.

\paragraph{Gossip and leader election.}
Gossip functions spread and combine values through repeated local exchanges.
%
The generic \texttt{gossip} function accepts a combination operator;
 \texttt{gossip\_\allowbreak max} and \texttt{gossip\_\allowbreak min} provide common specializations.
%
A stabilizing variant bounds propagation using a network-diameter parameter.
%
Leader election is exposed through \texttt{elect\_\allowbreak leaders}, which uses
 identifiers to break symmetry and a distance threshold to organize devices
 around distributed coordinators.
%
Combined with spreading and collection, it supplies the components needed
 for self-organizing coordination regions.

\paragraph{Native execution environment.}
The Simulator module supports testing and inspecting aggregate programs
 without tying the core library to a specific deployment.
%
A \texttt{Node} stores a device identifier, position, and arbitrary sensor
 data; an \texttt{Environment} manages nodes and determines their
 communication neighborhoods; and a discrete-event \texttt{Simulator}
 schedules program executions.
%
Neighborhood policies are pluggable, with built-in functions for
 radius-based communication, nearest-neighbor connectivity, and full connectivity.
%
Applications can supply custom policies to represent other communication relations.

Deployment utilities generate regular grids, deformed lattices, and random
 positions within circular regions.
%
Monitors receive callbacks at initialization, after events, and at completion,
 supporting logging, visualization, and metric collection.
%
This separation allows the same aggregate program to be inspected under
 different topologies and scheduling conditions without incorporating
 simulator-specific code into its coordination logic.

\paragraph{Channels between devices.}
A channel identifies devices around a route connecting a source and a target (\Cref{fig:channel}).
%
It can represent a spatial corridor for communication, routing, or coordinated
 activity.
%
\Cref{lst:phyelds-channel} first computes distances toward the target and
 then collects the source predicate along decreasing potential values.
%
The resulting field identifies a route from the source toward the target.
%
A second distance computation expands this route into a corridor of
 configurable width, producing a Boolean field that indicates membership.

\begin{lstlisting}[language=Python,breaklines=true,
  caption={Construction of a channel between a source and a target.},
  label={lst:phyelds-channel}]
@aggregate
def channel(width):
    distances = neighbors_distances()
    target_distance = distance_to(sense("target"), distances)
    nodes_in_path = collect_or(target_distance, sense("source"))
    distance_from_path = distance_to(nodes_in_path, distances)
    return distance_from_path < width
\end{lstlisting}

The program composes existing operators without managing routing tables or
 forwarding messages explicitly.
%
In the native simulation example, devices occupy a deformed
 $20 \times 20$ lattice, communicate within a fixed radius, and execute
 the program at intervals of $0.1$ seconds.
%
Source and target roles are supplied through sensor values, and a rendering
 monitor visualizes the channel as the computation evolves.

\paragraph{Self-organizing coordination regions.}
A second pattern partitions the network around elected leaders (\Cref{fig:scr}).
%
Each region combines three activities: information collection toward its
 coordinator, processing at that coordinator, and dissemination of the result.
%
\Cref{lst:phyelds-regions} instantiates this pattern by counting devices and
 broadcasting the count within each coordination region.

\begin{lstlisting}[language=Python,breaklines=true,
  caption={Counting devices within self-organizing coordination regions.},
  label={lst:phyelds-regions}]
@aggregate
def region_size():
    distances = neighbors_distances()
    leader = elect_leaders(4, distances)
    potential = distance_to(leader, distances)
    nodes = count_nodes(potential)
    return broadcast(leader, nodes, distances)
\end{lstlisting}

Leader election determines the distributed sources, the potential field
 organizes collection, and broadcast makes the regional result available
 to participating devices.
%
Replacing the counted value and accumulation function yields other
 applications of the same pattern, such as aggregating measurements or
 coordinating regional model updates.

\paragraph{Self-organizing federated learning.}
Phyelds allows regional coordination to operate directly on the outputs of
 local learning procedures.
%
In the example shown in~\Cref{lst:phyelds-sofl}, each device maintains
 its model parameters and a logical training counter, performs local
 training, and computes neighborhood distances from model performance
 on validation data.
%
These distances drive leader election and define the potential field used
 to collect updates.
%
A regional model is then broadcast and retained for the next local execution.

\begin{lstlisting}[language=Python,breaklines=true,
  caption={Illustrative coordination of self-organizing federated learning.
   Training, loss-based distances, and weight averaging are application helpers.},
  label={lst:phyelds-sofl}]
@aggregate
def client(initial_model_params):
    set_value, value = remember((initial_model_params, 0))
    local_model, tick = value

    evolved_model, train_loss = local_training(
        local_model, training_data
    )
    distances = loss_based_distances(
        evolved_model, validation_data
    )
    leader = elect_leaders(threshold, distances)
    potential = distance_to(leader, distances)
    models = collect_with(
        potential, [evolved_model], lambda x, y: x + y
    )
    aggregated_model = average_weights(models)
    area_model = broadcast(leader, aggregated_model, distances)
    set_value((area_model, tick + 1))
    return potential
\end{lstlisting}

The listing exposes the division of responsibilities: local training and
 weight averaging remain ordinary Python operations, while the aggregate
 functions determine federation structure and information flow.
%
It is an illustrative composition rather than a complete training protocol:
 coordination fields evolve across local rounds, and a complete implementation
 must also determine when collected updates are ready to be adopted.
%
The federation mechanisms and their evaluation are developed
 in~\Cref{chap:selforg-fl}.

\subsection{Integration with External Simulators}
\label{sec:phyelds-external-simulators}

The native simulator is one possible execution environment for Phyelds.
%
External integration requires two components: a simulator-specific runner
 and an environment adapter.
%
The runner executes actions produced by the aggregate programs and makes
 subsequent observations available for the next computation.
%
The adapter defines how simulated agents map to Phyelds devices, how their
 contexts are initialized and updated, and how neighborhoods are obtained.
%
This preserves the separation between the program's coordination logic and
 the simulation of physical dynamics.

The integration with the Vectorized Multi-Agent Simulator (VMAS) follows
 this structure through a dedicated runner and \texttt{VmasEnvironment}.
%
VMAS supplies the physical environment and agent state, while Phyelds
 supplies coordination through local state and neighbor interaction.
%
This integration is illustrated through a flocking example
 based on the Vicsek model (\Cref{fig:vmas-example}).
%
Agents move at a fixed speed and repeatedly align their direction with
 nearby agents, subject to a noise term.

Let $\mathbf{r}_i(t)$ be the position of agent $i$ and $\theta_i(t)$ its
 heading, with an interaction radius $\rho$.
%
For the neighborhood
 $\mathcal{N}_i(t)=\{j : \|\mathbf{r}_j(t)-\mathbf{r}_i(t)\|<\rho\}$,
 including the agent itself, the heading update can be written as
\begin{equation}
  \theta_i(t+\Delta t)=
  \operatorname{atan2}\!\left(
    \sum_{j\in\mathcal{N}_i(t)}\sin\theta_j(t),
    \sum_{j\in\mathcal{N}_i(t)}\cos\theta_j(t)
  \right)+\eta_i(t),
  \label{eq:phyelds-vicsek-heading}
\end{equation}
where $\eta_i(t)$ is the angular perturbation.
%
Expressing the average through its sine and cosine components accounts for
 the circular nature of headings.
%
The corresponding movement, using the current heading, is
\begin{equation}
  \mathbf{r}_i(t+\Delta t)=\mathbf{r}_i(t)+v\Delta t
  \begin{bmatrix}
    \cos\theta_i(t)\\
    \sin\theta_i(t)
  \end{bmatrix},
  \label{eq:phyelds-vicsek-position}
\end{equation}
with speed $v$.

At the implementation level, the aggregate program reads the agent's
 velocity from its context, obtains neighbor velocities through
 \texttt{neighbors}, computes the alignment direction and perturbation,
 and stores the next action for the runner.
%
The simulation shows initially disordered headings
 evolving toward coherent collective motion.
%
This example demonstrates the external execution interface; the policy
 learning methods discussed in~\Cref{chap:scalable-rl} build on the same
 ability to combine Python-based agent computation with field-based coordination.

\subsection{Role in the Thesis and Development Directions}

Phyelds provides the implementation layer connecting field-based coordination
 with Python-native learning code.
%
Its state and communication constructs specify how local computations evolve
 across the collective, while learning libraries retain responsibility for
 model representation, optimization, and inference.
%
The architecture supports the federation mechanisms
 in~\Cref{chap:selforg-fl}, the coordination of observations and collective
 information in~\Cref{chap:scalable-rl}, and decentralized application
 placement in~\Cref{chap:tasksplacement}.

The examples establish the framework's expressiveness and integration
 capabilities, but do not constitute a systematic performance comparison
 with other \gls{AC} implementations.
%
Further development includes performance and scalability measurements,
 broader simulator integration, and deployment in physical edge and robotic
 systems.
%
These directions complement the framework's present purpose as a practical
 environment for implementing and studying collective learning mechanisms.

\section[ProFed: Proximity-Based Federated Learning]{ProFed: A Benchmark for Proximity-Based Federated Learning}
\label{sec:selforgfl-benchmarking}
%=============================================================================

\subsection{Motivation and Scope}

Federated learning benchmarks provide common datasets, partitioning
 strategies, and evaluation protocols for comparing distributed learning methods.
%
FedScale~\cite{DBLP:conf/icml/LaiDSLZMC22}, for example, supports large-scale
 experiments that account for system heterogeneity and client resources.
%
LEAF~\cite{DBLP:journals/corr/abs-1812-01097} emphasizes reproducibility
 through standardized datasets, metrics, and reference implementations.
%
Other frameworks support configurable experiments with established datasets
 and client-level partitions~\cite{DBLP:journals/corr/abs-2007-13518,DBLP:journals/corr/abs-2007-14390}.

These tools cover many aspects of federated learning, but conventional
 client-level partitioning often leaves the spatial organization of data implicit.
%
In a \gls{CAS}, nearby devices may observe similar conditions because they
 operate within the same physical environment.
%
Traffic patterns within an urban district, measurements from sensors in a
 shared site, and observations from neighboring vehicles can therefore be
 correlated with location.
%
The resulting heterogeneity has a regional structure: devices within a
 region encounter similar distributions, while devices in different regions
 may encounter substantially different ones.

ProFed provides a benchmark for constructing this kind of
 scenario~\cite{DBLP:journals/jors/DominiIALV26}.
%
Instead of assigning heterogeneous partitions directly to individual clients,
 it introduces an intermediate regional layer.
%
A dataset is first partitioned among regions according to a selected
 heterogeneity strategy; each regional partition is then distributed among
 the devices assigned to that region.
%
The resulting datasets support controlled experiments in which spatial
 proximity is associated with data similarity.

The benchmark supplies data partitions rather than imposing a federation
 protocol or a communication topology.
%
Researchers can use the same regional distributions to compare global,
 clustered, personalized, or decentralized learning methods.
%
In this thesis, this is particularly useful for evaluating the methods
 in~\Cref{chap:selforg-fl}, whose coordination mechanisms exploit relationships
 between device proximity and local learning conditions.

\subsection{Regional System Model}
\label{sec:profed-system-model}

Consider an operating area partitioned into $K$ contiguous regions
 $\mathcal{R}=\{R_1,\ldots,R_K\}$ and a set of devices
 $\mathcal{V}=\{1,\ldots,n\}$.
%
An assignment $r:\mathcal{V}\rightarrow\{1,\ldots,K\}$ maps each device
 to its region, with multiple devices typically assigned to each region.
%
Region $R_k$ is associated with a joint data distribution $P_k(X,Y)$.
%
The local dataset of device $i$ is
\begin{equation}
  D_i=\{(x_{i,s},y_{i,s})\}_{s=1}^{m_i},
  \qquad (x_{i,s},y_{i,s})\sim P_{r(i)}.
  \label{eq:profed-local-data}
\end{equation}
This notation describes the intended statistical model; the benchmark
 realizes it through finite partitions of an existing dataset.

Devices assigned to the same region share an underlying distribution,
 although their empirical datasets need not have identical label proportions.
%
Across regions, the distributions may differ according to the selected
 partitioning method.
%
The IID configuration is a special case in which the regional distributions
 are the same.
%
Thus, regional membership determines the source of local data without
 requiring samples within a region to be close under a feature-space metric,
 or requiring the supports of different regions to be disjoint.

The distinction matters because proximity in ProFed concerns the spatial
 assignment of devices and the distributions from which they receive data.
%
For the classification datasets, the implemented strategies primarily
 control regional label frequencies.
%
They do not by themselves reproduce all forms of geographic variation,
 such as changes in image acquisition conditions or temporal environmental drift.
%
The regional model is therefore a controlled abstraction for studying
 spatially structured heterogeneity.

\subsection{Partitioning Strategies}
\label{sec:profed-partitioning}

ProFed implements IID, Dirichlet, and hard partitioning, together with a
 custom distribution interface.
%
The first stage determines how examples are assigned to regions; the second
 distributes each region's data among its devices.
%
This common structure makes the partitioning strategy independent of the
 learning algorithm used in the experiment.
%
\Cref{fig:skewness} illustrates the three built-in patterns for five regions.

\paragraph{IID partitioning.}
The IID strategy distributes data so that regional partitions approximate
 the original dataset's label proportions.
%
Devices receive local subsets from comparable regional distributions,
 providing a baseline against which the effects of heterogeneity can be assessed.
%
Finite partition sizes may still produce sampling differences, but there is
 no intended regional label specialization.

\paragraph{Dirichlet partitioning.}
The Dirichlet strategy produces regional label imbalance while allowing
 labels to be represented in multiple regions.
%
Its concentration parameter $\alpha$ controls the dispersion of allocation
 proportions: smaller values favor more concentrated assignments, whereas
 larger values tend toward more even allocations.
%
Unlike a hard split, a region is not explicitly restricted to a prescribed
 label subset, although a finite realization can leave some labels absent.
%
The ProFed evaluation uses $\alpha=0.5$ as its Dirichlet configuration.

This parameter controls statistical heterogeneity at the regional level.
%
After allocation, devices within a region receive subsets of the same
 regional pool, preserving the intended association between regional
 membership and distributional similarity.
%
The construction consequently differs from assigning an independent
 Dirichlet partition to every device, which need not create any relationship
 between location and label distribution.

\paragraph{Hard partitioning.}
Hard partitioning restricts each region to a subset of labels.
%
This yields pronounced regional specialization and can create local training
 sets that omit much of the global label space.
%
ProFed supports balanced label-subset sizes as well as configurable
 cardinalities for individual regions.
%
The resulting scenario is useful for examining how learning methods behave
 when updates are trained on sharply different regional tasks.

\paragraph{Custom distributions.}
For finer control, users can supply a distribution matrix
 $W\in[0,1]^{L\times K}$, where $L$ is the number of labels and $K$
 the number of regions.
%
Entry $W_{\ell k}$ specifies the proportion of examples with label $\ell$
 assigned to region $R_k$.
%
When all examples are allocated, the proportions satisfy
\begin{equation}
  \sum_{k=1}^{K}W_{\ell k}=1,
  \qquad \ell=1,\ldots,L.
  \label{eq:profed-distribution-matrix}
\end{equation}
These are allocation proportions for each label, rather than label
 probabilities conditioned on a region.
%
If the original dataset contains $N_\ell$ examples with label $\ell$,
 the intended number allocated to region $k$ is proportional to
 $N_\ell W_{\ell k}$, subject to integer allocation.
%
Consequently, the regional label frequencies also depend on the label counts
 in the source dataset.

\subsection{Implementation and Supported Datasets}
\label{sec:profed-implementation}

ProFed is implemented in Python using
 PyTorch~\cite{DBLP:conf/asplos/AnselYHGJVBBBBC24} and
 TorchVision~\cite{TorchVision}.
%
Its API covers dataset acquisition, training--validation splitting,
 regional partitioning, and allocation to devices.
%
Local partitions are exposed through PyTorch's \texttt{Subset} class,
 allowing existing training code to consume them through familiar dataset
 and data-loader interfaces.
%
This avoids requiring learning algorithms to adopt a benchmark-specific
 representation of examples.

The supported datasets span handwritten characters, clothing categories,
 small color images, and face images for age estimation.
%
\Cref{tab:datasets} summarizes their sizes and input characteristics.
%
MNIST~\cite{lecun2010mnist} supplies handwritten digits and serves as a
 relatively compact baseline.
%

 dimensions but replaces digits with clothing categories.
%
The EMNIST letters configuration~\cite{DBLP:journals/corr/CohenATS17}

 classes, respectively, allowing experiments with different label-space sizes.
%

%

 transferred directly to the learning objective.

\subsection{Benchmark API and Experimental Workflow}
\label{sec:profed-api}

The API follows the two-stage partitioning process explicitly.
%
First, \texttt{download\_\allowbreak dataset} retrieves the selected dataset and its
 test split.
%
The training data can then be divided into training and validation subsets
 through \texttt{split\_\allowbreak train\_\allowbreak validation}.
%
Next, \texttt{partition\_\allowbreak to\_\allowbreak subregions} creates an environment containing
 regional partitions for the chosen strategy.
%
Finally, \texttt{from\_\allowbreak subregion\_\allowbreak to\_\allowbreak devices} produces local subsets for
 the devices assigned to each region.

\Cref{lst:api-example} illustrates this workflow using EMNIST and hard
 partitioning.
%
The spatial assignment is supplied by the experiment: the application-defined
 \texttt{distribute\_\allowbreak nodes\_\allowbreak spatially} helper returns a mapping from regional
 identifiers to lists of device identifiers.
%
ProFed uses this assignment to associate regional data with the corresponding
 devices, while the simulator or deployment code determines their actual positions.

\lstdefinestyle{proFedStyle}{
  basicstyle=\ttfamily\scriptsize,
  breaklines=true,
  captionpos=b,
  language=Python,
  showstringspaces=false,
  tabsize=4,
  breakatwhitespace=false,
  breakindent=12pt,
}

\begin{lstlisting}[style=proFedStyle,
  caption={Partitioning EMNIST across regions and their devices.
   Spatial deployment is provided by an application-defined helper.},
  label={lst:api-example}]
from ProFed.partitioner import (
    download_dataset,
    split_train_validation,
    partition_to_subregions,
)

mapping_devices_area = distribute_nodes_spatially(
    devices, number_subregions
)
train_data, test_data = download_dataset("EMNIST")
train_data, validation_data = split_train_validation(
    train_data, 0.8
)
environment = partition_to_subregions(
    train_data, validation_data, "Hard", number_subregions, seed
)

mapping_devices_data = {}
for region_id, region_devices in mapping_devices_area.items():
    local_partitions = environment.from_subregion_to_devices(
        region_id, len(region_devices)
    )
    for device_index, data in local_partitions.items():
        device_id = region_devices[device_index]
        mapping_devices_data[device_id] = data
\end{lstlisting}

The test split remains available separately from the regional training and
 validation subsets.
%
This allows evaluation against a common held-out dataset as well as
 inspection of region-specific behavior during training.
%
Because the generated partitions are ordinary PyTorch subsets, model
 architecture, local optimization, client participation, and aggregation
 remain choices of the experimental learning protocol.

Reproducibility requires recording the dataset, partitioning method,
 regional configuration, device assignment, and random seed alongside the
 training hyperparameters.
%
These settings determine the experimental instance on which competing
 methods are compared.
%
The regional layer additionally permits controlled studies that vary the
 number of regions or their data distributions while retaining the same
 local learning implementation.

\subsection{Reuse, Availability, and Role in the Thesis}

ProFed is distributed as an open-source Python package under the MIT
 license\footnote{\url{https://github.com/davidedomini/ProFed}}.
%
The benchmark release is archived on
 Zenodo\footnote{\url{https://doi.org/10.5281/zenodo.16367696}}.
%
Its partitioning interface supports reuse with existing PyTorch training
 pipelines, while additional datasets and allocation strategies can extend
 the range of experimental scenarios.
%
The custom distribution matrix is particularly useful when an experiment
 requires regional structures beyond the predefined strategies.

Within this thesis, ProFed supplies controlled regional data heterogeneity
 for the evaluation of self-organizing federated learning
 in~\Cref{chap:selforg-fl}.
%
The benchmark's regions define the origin of local data; they are not
 prescribed federations that an algorithm must adopt.
%
This distinction allows experiments to examine whether the coordination
 mechanism discovers useful learning groups from local information.
%
When combined with Phyelds, data generation and federation coordination
 remain separate components, making it possible to vary one while keeping
 the other fixed.

Further development includes additional datasets, a wider set of clustered
 and personalized learning baselines, and systematic comparisons between
 regional and conventional client-level partitioning.
%
These extensions would help characterize when spatially structured
 heterogeneity changes convergence, robustness, or the relative behavior
 of federated learning methods.

\section[Project Emerge]{Project Emerge: A Toolchain for Robot Teams}
\label{sec:project-emerge}
%=============================================================================

\subsection{Motivation and Deployment Requirements}

Field-based coordination provides abstractions for expressing collective
 behavior independently of the low-level interactions among devices.
%
Bringing these abstractions to physical robot teams, however, requires an
 execution infrastructure that connects aggregate programs with localization,
 communication, and actuation.
%
A program that operates on positions, neighborhood relations, and movement
 intentions must receive suitable representations of the physical environment
 and translate its outputs into commands that the robots can execute.
%
These requirements introduce an engineering gap between the computational
 model and a working robotic deployment.

Project Emerge addresses this gap through an open-source toolchain for
 executing and demonstrating aggregate programs on mobile robot
 teams~\cite{DBLP:journals/scp/FarabegoliABCDPV}.
%
It combines camera-based localization, configurable neighborhood management,
 aggregate execution, robot control, and an interactive web dashboard.
%
A compatible simulation environment supports development and inspection
 before physical deployment.
%
The toolchain builds on ScaFi~\cite{DBLP:journals/softx/CasadeiVAP22} for
 aggregate execution and
 MacroSwarm~\cite{DBLP:journals/lmcs/AguzziCV25} for collective behavior
 abstractions, extending them with the infrastructure needed to connect
 programs to a physical team.

The design separates the collective program from the mechanisms used to
 observe and control the robots.
%
Localization must provide both position and orientation, since directional
 information is required to translate spatial intentions into movement.
%
Neighborhood relations must reflect the current deployment and remain
 configurable as robots move.
%
Actuation must expose a common interface while accommodating the control
 mechanisms of a particular platform.
%
Finally, monitoring and interaction must make collective behavior visible
 and allow changes to programs, parameters, and environmental conditions
 during execution.

Within the infrastructure presented in this chapter, Project Emerge
 supplies a physical demonstration environment for field-based coordination.
%
Its implementation is distinct from Phyelds: the aggregate runtime uses
 Scala and ScaFi, while Python supports localization and robot emulation.
%
The shared foundation is the aggregate execution model, which connects
 local sensing and state evolution with collective behavior.

\subsection{Architecture and Execution Model}
\label{sec:emerge-architecture}

The architecture comprises a localization subsystem, a Neighborhood System,
 an Aggregate Runtime, a Dashboard, and the robots themselves.
%
An MQTT message broker connects these components through a publish--subscribe
 interface.
%
\Cref{fig:emerge-architecture} distinguishes the system-level organization
 from the execution cycle inside the aggregate runtime.

    \label{fig:emerge-system-architecture}
  \end{subfigure}\hfill
  \begin{subfigure}[t]{0.40\textwidth}

  \label{fig:emerge-architecture}

\paragraph{Localization and neighborhood construction.}
The physical deployment uses an external camera and ArUco markers to
 identify robots and estimate their positions and orientations.
%
The detector is implemented with OpenCV and publishes pose information
 together with robot identifiers through MQTT.
%
The Neighborhood System derives logical communication relations from
 the spatial deployment using replaceable proximity policies.
%
This makes neighborhood membership an explicit part of the experimental
 configuration, allowing the interaction radius to be changed independently
 of the aggregate program.

\paragraph{Aggregate environment.}
The runtime maintains a representation of the environment containing,
 for each robot, its identifier, position, orientation, sensing values,
 neighborhood relations, and aggregate execution state.
%
An \emph{Environment Provider} constructs this representation from the
 information supplied by the surrounding components.
%
The \emph{AC Orchestrator} evaluates the aggregate program using the
 corresponding robot contexts, and an \emph{Environment Update} translates
 the resulting actions into commands published to the robots.
%
These three abstractions implement the sense--compute--actuate cycle:
 observing the current environment, computing collective actions through
 per-robot program evaluations, and applying the resulting commands.

The current implementation executes the aggregate runtime on a central
 server and maintains a separate execution context for each robot.
%
Aggregate state and logical neighborhood exchanges are managed in memory
 within that process, while communication with the physical devices occurs
 through MQTT.
%
The programming model retains local state and neighborhood-based
 computation, but its execution is centrally orchestrated at a fixed frequency.
%
This arrangement simplifies integration and provides control over the
 demonstration environment; it does not evaluate the network-level behavior
 of a fully distributed aggregate runtime.

At each cycle, the runtime constructs the environment from the latest
 available updates.
%
This favors responsiveness to the current robot configuration, without
 requiring every physical component to produce an update simultaneously.
%
Nevertheless, the resulting control depends on the freshness and accuracy
 of localization and on the delivery of actuation commands.
%
The centralized execution of logical neighbor exchanges does not remove
 these dependencies at the interface with the physical environment.

\paragraph{Actuation interface.}
Aggregate programs produce movement intentions through an
 \texttt{Actuation} type.
%
Its alternatives include a \texttt{Rotation}, a \texttt{Forward} vector,
 and \texttt{NoOp} or \texttt{Stop} commands.
%
The actuation backend maps these outputs to platform-specific controls;
 in the demonstrated deployment, velocity vectors are converted into
 differential-drive wheel speeds.
%
This separates the specification of collective motion from the mechanics
 of a particular robot, while supporting alternative platforms through
 additional control backends.

\subsection{Programming Interface and Experimental Workflow}
\label{sec:emerge-workflow}

The aggregate runtime is implemented in the
 \texttt{aggregate-runtime} subproject.
%
Its core package contains the orchestrator and environment interfaces,
 while deployment-specific components reconstruct robot state from MQTT
 messages and publish the resulting commands.
%
In particular, \texttt{MqttEnvironmentProvider} supplies the environment
 and \texttt{RobotUpdateMqtt} implements the actuation update.
%
The execution loop composes these components with the selected aggregate
 program and a rendering interface.

An executable collective program extends \texttt{BaseDemo}, whose entry
 point returns an actuation command for the current robot context.
%
\Cref{lst:emerge-program-interface} shows this interface.
%
The runtime repeatedly evaluates the same program across the team's
 contexts, maintaining the state and aligned neighborhood information
 required by ScaFi.

\begin{lstlisting}[language=scala,breaklines=true,
  caption={Entry point for collective robot programs in Project Emerge.},
  label={lst:emerge-program-interface}]
trait BaseDemo extends AggregateProgram:
  override def main(): Actuation
\end{lstlisting}

For example, the \texttt{PointTheLeader} behavior orients robots toward a
 leader selected through the dashboard.
%
It uses \texttt{gradientCast} to propagate a vector field from the selected
 leader and produces rotation commands according to the resulting field.
%
Leader selection changes the source of the collective computation, while
 the same program continues to execute across the team.
%
The runtime also supports switching among preloaded programs and updating
 their parameters during operation.

Communication separates per-robot information from shared control inputs.
%
Per-robot MQTT topics use the structure
 \texttt{robots/<robot\_id>/<topic>}, including pose and neighborhood updates.
%
Shared topics carry sensing inputs, program selection, and leader identity.
%
This organization allows localization, control, and visualization components
 to interact with the runtime through a common communication interface.

A Docker Compose configuration assembles the broker, aggregate runtime,
 dashboard, and neighborhood services.
%
The same runtime can operate with physical robots or with a Python-based
 emulation environment\footnote{\url{https://github.com/Project-Emerge/robot-emulation}}.
%
The emulator replaces the robots and physical localization system while
 retaining the MQTT interfaces used by the rest of the toolchain.
%
Consequently, aggregate programs and the dashboard can be exercised before
 connecting physical hardware.

\paragraph{Monitoring and interaction.}
The web dashboard displays robot positions and neighborhood relations,
 exposes program selection and interaction parameters, and provides
 robot-specific controls and leader assignment.
%
\Cref{fig:emerge-dashboard} shows the interface.
%
Interactive position manipulation and parameter changes support inspection
 of how a collective program responds to an altered configuration.
%
The dashboard therefore serves both as a control interface and as a means
 of making the relationship between local interactions and collective
 behavior visible to users.

\subsection{Scope, Limitations, and Development Directions}
\label{sec:emerge-limitations}

Project Emerge demonstrates the integration of aggregate execution with
 physical sensing and actuation in a small robot team.
%
The current deployment relies on external camera-based localization and
 centralized orchestration, which constrain its operating environment
 and distinguish it from an autonomous distributed robot swarm.
%
The live demonstrations establish practical usability and qualitative
 recovery from perturbations, but do not provide systematic measurements
 of convergence time, scalability, or robustness across controlled levels
 of noise and communication failure.

A principal development direction is fully distributed execution,
 with each robot hosting its own aggregate runtime and managing local
 communication.
%
Indoor localization based on ultra-wideband technology is a candidate
 for reducing dependence on an external camera.
%
Additional actuation backends would extend the toolchain to aerial and
 legged robots, while richer dashboard and augmented reality interfaces
 could improve monitoring and interaction with physical and emulated teams.

Further directions include introducing communication delays into the
 emulation environment, evaluating controlled sensing and execution
 perturbations, and investigating natural-language generation of aggregate
 programs.
%
Together, these extensions would broaden the infrastructure's applicability
 and support more systematic study of the gap between aggregate models,
 simulated execution, and physical collective behavior.

Project Emerge is released under the MIT license, with the system source
 available in a public
 repository\footnote{\url{https://github.com/Project-Emerge/Project-Emerge-system}}
 and an archived release on
 Zenodo\footnote{\url{https://doi.org/10.5281/zenodo.18224119}}.

The companion robot hardware is also available as an open
 design\footnote{\url{https://github.com/Project-Emerge/rover-circuit}}.
%
The separation of localization, aggregate execution, communication,
 and actuation permits components to be adapted while retaining the
 collective programming interface.

For this thesis, the demonstrator complements the programming and
 benchmarking tools by showing how field-based coordination can be
 connected to physical devices.
%
The demonstrated robot behaviors use explicitly programmed coordination rules.
%
Project Emerge supplies infrastructure that could support their future
 physical evaluation, including observation of collective behavior and
 interaction with environmental perturbations.

 components and assessing their execution and resource requirements within
